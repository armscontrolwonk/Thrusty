# Library reset: plan (2026-10-02, for the user's review; nothing here is built)

## The problem

Thrusty ships 45 vehicle files (13 boosters, 12 reentry objects, 13 flight
plans, 7 reentry plans) and two more at the repo root. They are presented to
a user as models. Several have turned out not to be trustworthy:

- AUR was entered as liquid when it is solid, and its first stage carried
  the whole vehicle's length.
- The Strypi strap-ons have no length, so they are flown as 0.46 m stubs.
- The Generic ICBM flies on a custom drag table with no source that no
  screen shows; Shahab-3 and Taepodong-II fly on stored copies of Forden's.
- Minotaur-IV (AI-coded) has no source and no notes.
- SWERVE's mass and lift were chosen to keep a test case alive, by its own
  notes.
- 11 of 13 booster files have an empty `source`; four have no notes.

The user has proposed deleting them more than once. On 2026-09-19 a wipe
was argued down for two practical reasons, neither of which is a reason to
trust the data:

1. 38 of 66 test files load shipped vehicles by name; emptying the
   libraries makes parametrised tests skip silently instead of failing.
2. Files in `~/Documents/Thrusty` override shipped ones; deleting the
   shipped copies leaves older user forks as the only library.

## The idea

Today one set of files does two jobs: it exercises the code in tests, and
it is the library a user sees. Split them.

- **Fixtures**: the current files, moved where tests read them and users do
  not, labelled as unverified.
- **Shipped library**: empty, then filled one vehicle at a time through a
  gate.

## Phases

### Phase 0 — inventory (no file moves)

A core module, `library_audit.py`, with a test, that reports for every file
in the four libraries: every stored value that differs from the default;
whether a run actually uses it (the drag table check of 2026-10-02 is the
model: which source is flown, not which is stored); where a person can see
it (editor, schematic, 3-D, nowhere); and what the file says about its
source. Output: `LIBRARY_INVENTORY.md`, regenerated by a script, for the
user to read. This is the evidence for everything after, and it is useful
even if the rest is never done.

### Phase 1 — fixtures

- Move the 47 files, unchanged byte for byte, to
  `tests_data/vehicles/{booster_library,ro_library,flight_plans,reentry_plans}`.
- `booster_models` resolves its four bundled directories through one
  function; `conftest.py` points it at the fixtures. Tests keep their
  vehicle names and their golden outputs.
- A test asserts that the fixtures directory is not the shipped one and
  that the app bundle does not include it.
- Each fixture's status is stated in a `README` in that folder, not by
  editing the files (editing them would move every golden).

### Phase 2 — an empty shipped library

- The four shipped directories hold nothing (or one worked example: a
  decision below).
- The app must open cleanly with no vehicles: an empty-state message, "New
  vehicle" working from nothing, every dialog that lists vehicles tolerant
  of an empty list. This needs checking screen by screen; nothing in the
  non-test code names a vehicle, which helps.
- The 25 tests that walk the shipped directories by path are re-pointed:
  the schema and split tests run over fixtures AND shipped, so an empty
  shipped directory cannot silence them.

### Phase 3 — the admission gate

A shipped file is accepted only if a test can verify, from the file alone:

1. **Every stored hardware value has a provenance entry**: the value, where
   it came from, and its kind — measured from imagery, published,
   estimated (naming the estimator), or assumed. `docs/ingestion/` already
   holds a per-field provenance schema designed in June and never wired
   in; it is stale but is the starting point.
2. **Nothing is fitted**: no value whose stated basis is that a run needed
   it.
3. **Nothing is flown unseen**: no stored drag table without a source and a
   schematic flag saying a table is flown; every field has a declared place
   where a person sees it (a visibility registry, like `field_registry.py`,
   so an undeclared field fails the suite).
4. **Drawn ≡ flown**: the schematic's and 3-D export's flags are either
   empty or each acknowledged in the file with a reason.
5. **Plans carry their source too**: what the flight plan reproduces (a
   reported apogee, range, or impact zone) and where that was reported.

### Phase 4 — the user's own folder

`~/Documents/Thrusty` holds 2 boosters, 13 objects, 29 flight plans and 23
reentry plans. With the shipped library empty these are no longer overrides
of anything; they are simply the user's files. The startup report that
lists overrides changes to say so. Nothing in that folder is deleted or
moved by Thrusty. A one-time, explicit offer to move them into an
`unverified` subfolder is possible; it is the user's choice per machine.

### Phase 5 — documents

- `BENCHMARKING.md`: each comparison states which fixture it rests on and
  that the fixture is unverified, until that vehicle passes the gate.
- `README.md`, `CLAUDE.md` ("Data provenance"), `METHODS.md` where they
  describe the shipped vehicles.
- `LIBRARY_INVENTORY.md` from Phase 0 stays as the record of why.

### Phase 6 — re-admission, one vehicle at a time

The user picks the order. Each vehicle gets a provenance sheet the user
reviews line by line; Claude can fill in what the file and the cited
papers say, and must not supply a number from memory.

## Decisions taken (user, 2026-10-02)

- **Rename the fixtures** so nobody mistakes them for models (decision 1).
  The naming scheme is still to be agreed.
- **Ship empty** (decision 2).
- **Provenance** as recommended, for now: per field for hardware numbers,
  per file for plans (decision 3).
- **AUR is the first vehicle to re-admit** (decision 5).
- **Stand-ins are not loadable in the app** (decision 4).
- **Phase 0 first** (decision 6): done 2026-10-02, `library_audit.py` and
  `LIBRARY_INVENTORY.md`.
- The key from old names to stand-in names was emailed to the user and is
  deliberately not in the repository.

"Fixture" here means a file kept only so the tests have something to run
on: a stand-in input whose job is to exercise the code, not to describe a
real vehicle.

## Decisions as first put to the user

1. **Fixture names.** Keep the real names ("Scud-B (R-17)") in the fixtures,
   or rename them so their status is unmistakable ("fixture-A")? Renaming
   touches 38 test files and every golden. Recommendation: keep the names;
   the folder and its README carry the label.
2. **Empty, or one example?** Ship nothing, or one fully sourced worked
   example so a new user has something to open? Recommendation: nothing
   until the first vehicle passes the gate.
3. **How fine the provenance.** Per field, or per file with exceptions
   listed? Recommendation: per field for hardware numbers; per file for
   plans.
4. **Fixtures in the app.** Should fixtures be loadable at all outside
   tests (a developer switch)? Recommendation: no switch in the app;
   anyone who wants one can copy a file into their own folder, where the
   startup report will show it.
5. **The first vehicle to re-admit.**
6. **Order of work.** Recommendation: Phase 0 first, alone. It moves
   nothing and tells us how bad each file is.

## Costs

- The app opens with an empty vehicle list until vehicles are re-admitted.
- Published comparisons in BENCHMARKING.md rest on unverified inputs and
  must say so.
- Phases 1–3 are roughly: one path function and a conftest change; an
  empty-state pass over the GUI; a provenance schema, a visibility
  registry and their tests. The GUI pass is the least predictable.
